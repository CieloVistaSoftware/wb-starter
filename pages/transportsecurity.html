Transport Security

TLS, HSTS, how TLS agrees on secrets, and what it takes to secure an API message.

1. TLS — Transport Layer Security

TLS secures a connection between two endpoints (browser and server, service and service). It provides three things:

  • Encryption — nobody on the path can read the data.
  • Integrity — any change to the data in transit is detected.
  • Authentication — the client knows it is talking to the real server (via its certificate); with mutual TLS, the server knows the client too.

Two protocols inside TLS

  • Handshake protocol — negotiates the version and cipher suite, authenticates the server, and agrees on the keys.
  • Record protocol — carries the application data, split into records, each encrypted and integrity-protected with those keys.

Versions

  • TLS 1.3 (2018) — current; faster one-round-trip handshake, only forward-secret key exchange, only AEAD ciphers.
  • TLS 1.2 (2008) — still common and acceptable when configured with modern cipher suites.
  • TLS 1.0 / 1.1 — deprecated (RFC 8996, 2021); disable them.

2. HSTS — HTTP Strict Transport Security

HSTS is a response header that tells the browser: for this site, use HTTPS only, for the given time. After the browser has seen it, it rewrites any http:// link to https:// itself and refuses to let the user click through certificate errors. That closes the gap where an attacker downgrades the first plain-HTTP request.

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  • max-age=31536000 — remember the rule for one year (in seconds).
  • includeSubDomains — apply it to every subdomain too.
  • preload — consent to be listed in the browsers' built-in HSTS preload list, so even the very first visit uses HTTPS.

3. How TLS exchanges secrets

The key is never sent across the network. Both sides compute it.

  1. Ephemeral key agreement (ECDHE — Elliptic Curve Diffie-Hellman Ephemeral). Client and server each make a fresh key pair for this connection and send only the public half (in ClientHello / ServerHello). Each combines its own private key with the other's public key, and both arrive at the same shared secret. An eavesdropper who sees both public values cannot compute it. Because the key pairs are thrown away afterwards, a later theft of the server's long-term key cannot decrypt recorded traffic (forward secrecy).
  2. Server authentication. The server sends its certificate and signs the handshake transcript with the certificate's private key (CertificateVerify). The client checks the certificate chain and the signature, so it knows the public value it used came from the real server, not a man in the middle.
  3. Key derivation (HKDF — HMAC-based Key Derivation Function). The shared secret is fed through HKDF-Extract and HKDF-Expand, mixed with a hash of the handshake so far, to derive separate secrets for separate jobs:
    • handshake traffic secrets — encrypt the rest of the handshake;
    • application traffic secrets — encrypt the application data, one per direction;
    • resumption secret — lets a later connection resume without a full handshake;
    • exporter secret — keys that higher-level protocols can derive from the session.
  4. Symmetric encryption (AEAD — Authenticated Encryption with Associated Data). From here on every record is encrypted and authenticated with a fast symmetric cipher such as AES-GCM or ChaCha20-Poly1305.

4. API message security

TLS protects the pipe, not the message. Once a request arrives and TLS is terminated (at a load balancer, a gateway, or the server), the message is plain again. Who sent it, whether it was altered after that point, and whether it is a replay are separate questions, answered by separate layers.

HMAC (Hash-based Message Authentication Code) in the table is a cryptographic primitive, a keyed hash, not a protocol; protocols and token formats such as signed JWTs are built on it.
