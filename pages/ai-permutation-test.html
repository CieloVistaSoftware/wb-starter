How to Use This Tool

Schema-driven combinatorial testing — reads your behavior schemas, finds gaps in test coverage, and tells you exactly how to fix them.

1
Select a Schema

Pick any *.schema.json from the dropdown. The tool fetches it live from src/wb-models/ and parses it.

2
Dimensions Are Extracted Automatically

Every property with an enum array, a boolean type, or a set of defined values becomes a testable dimension. For example, variant with 7 enum values = 7 options, and any boolean property becomes a 2-value dimension (true/false). These are the axes of your test matrix.

3
Existing Coverage Is Shown

The schema's test.matrix.combinations array is displayed. These are the combos you already test. The tool fingerprints each one so it can diff against what's generated.

4
Missing Permutations Are Computed

Pairwise mode (default): Generates the minimum set of test cases where every pair of values across every pair of dimensions appears at least once. This catches interaction bugs (e.g., "pill + error variant breaks layout") while reducing test count by 80–90% vs full cartesian.

Full cartesian: Every possible combination. Use this for small schemas (≤3 dimensions). For badge with 7 variants × 4 sizes × 4 booleans = 448 combos — that's too many, use pairwise.

5
Each Gap Is Explained With a Fix

Every missing permutation shows: what combination is untested, why it matters (which interaction it covers), suggested HTML markup, and the JSON to paste into your schema's test matrix.

💾 Save Missing to Schema writes all missing permutations directly into the schema file — both test.matrix.combinations (JSON) and test.setup (HTML lines) — via the dev server's /api/save endpoint. One click, no copy-paste. The page auto-reloads the schema afterward so coverage stats update immediately.

6
Run All Tests Live

Click ▶ Run All Tests Live to inject every missing permutation as a real DOM element right here in the browser. The runner creates each <wb-*> element, sets the attributes from the combo, waits for WB to initialize the behavior, then verifies 5 things:

① Element exists in DOM — ② Root CSS class is present (e.g., x-badge) — ③ Each appliesClass from the schema is applied (e.g., x-badge--primary) — ④ Element has visible dimensions (not 0×0) — ⑤ Element is not hidden via CSS.

Failures show the expected vs. actual value and a suggested fix pointing to the specific ViewModel or CSS file to update.
